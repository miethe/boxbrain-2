## BACKEND
The backend (FastAPI + use-case layer) is materially more complete than a scaffold: all 46 OpenAPI paths have matching route handlers, the frontend api.ts client hits real paths that exist, the Alembic chain is a single linear chain (0001->0005, no branching heads), and the dual-mode repository (in-memory default / SQLAlchemy via BOXBRAIN_REPOSITORY=database) uses a consistent duck-typed `_save_*`/`getattr(repository, 'save_x', None)` hook pattern so most governance mutations (approval/freshness/canonical/review actions) correctly persist to Postgres and write audit events when DB mode is active. The real gaps are: (1) pagination is a total placeholder across every list endpoint (nextCursor is hardcoded None everywhere, and the frontend already sends cursor/limit/mode params the backend silently drops), (2) `/api/assets/{key}` has zero actor/visibility enforcement despite every JSON endpoint enforcing restricted-object filtering, (3) the whole frontend runs as `x-boxbrain-user: admin` by default with no in-app role switcher, so restricted-visibility code paths are never exercised in practice, (4) three whole feature domains (build/export manifests, Collections, real AI enrichment/ai_outputs) have SQL tables scaffolded in infra/initial_db_schema.sql but zero ORM models, use-cases, or routes wired to them, and (5) the containerized app stack boots DB mode with `seed=False` and no seed script, so a fresh stack has an empty catalog until someone manually ingests a deck. ### db risks
- Empty catalog on fresh boot: infra/docker-compose.app.yml sets BOXBRAIN_REPOSITORY=database for the full containerized stack, and dependencies.py constructs SqlAlchemyBoxBrainRepository(SessionLocal, seed=False) — there is no seed/fixture script for Postgres (no `make seed-db`, nothing under any 'seed' path) equivalent to the rich in-memory seed() fixture (ROI/architecture/restricted families, seeded WorkProduct, ContentBlock, Storyboard, review items). - Hard startup dependency on migration completion with no retry/backoff: `repository` is a module-level singleton built at import time in app/dependencies.py; SqlAlchemyBoxBrainRepository.__init__ calls reload() immediately, which SELECTs from tables that must already exist. infra/docker-compose.app.yml correctly gates the api service on `migrate: condition: service_completed_successfully` and `postgres: condition: service_healthy`, but running the API standalone (e.g. `make api-db`, or a bare uvicorn invocation per README/AGENTS.md examples) without first running `alembic upgrade head` will crash hard at import with no graceful wait or clear remediation message.
- Stale-cache risk from reload() merge semantics: reload() populates self.* dicts via `.update(...)`, which adds/overwrites but never removes entries — rows deleted directly in Postgres out-of-band (manual cleanup, another process) will keep appearing as present in a running API process's in-memory read model until restart.

- No connection pool sizing/env exposed in config.py/database.py (create_engine uses SQLAlchemy defaults); combined with the reload()-heavy access pattern (broad SELECT scans triggered by ordinary mutation requests), concurrent pilot load could hit pool exhaustion or slow full-table reloads well before real data volume grows large.
- BOXBRAIN_DB_SCHEMA (custom Postgres schema support) only adjusts search_path/version_table_schema; migration 0001 unconditionally runs `CREATE EXTENSION IF NOT EXISTS vector`/`uuid-ossp` from infra/initial_db_schema.sql — worth explicitly verifying extension creation behavior when a non-default BOXBRAIN_DB_SCHEMA is set, since this path isn't covered by the migration chain's own tests.
